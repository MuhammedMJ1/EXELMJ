# EXELMJ Word Mode — Open-Source Decision Document

Scope: what to adopt, in what order, and what to never touch. Every item below is from the verified inventory. Versions and licences as verified 2026-08-18/19.

**One cross-cutting decision to make first:** the Tiptap ex-Pro extensions and `tiptap-footnotes` both exact-pin `@tiptap/core` **3.30.2**, while EXELMJ pins **3.30.0**. Bump the whole Tiptap set to 3.30.2 in one commit before starting any of this, or half the list is blocked.

---

## 1. TOP RECOMMENDATIONS (ranked)

### 1. Chromium print fragmentation via Electron `webContents.printToPDF` — **ADOPT NOW**
https://github.com/electron/electron — MIT (Electron) / BSD-3-Clause (Chromium). Already a dependency.
**Gains:** repeating table header rows on printed pages, running "Page X of Y" headers/footers, print date/title — with **zero new packages**. `printToPDF` supports `displayHeaderFooter`, `headerTemplate`, `footerTemplate`, and Chromium injects the classes `date`, `title`, `url`, `pageNumber`, `totalPages` (verified in Electron docs).
**Plugs into:** `src/word/printDoc.ts` (`buildDocPrintHtml`), `src/word/pageSetup.ts`.
**Effort:** hours. Add `thead { display: table-header-group; break-inside: avoid; }` + `tfoot { display: table-footer-group; }` and test on a real 3-page Arabic table. Caveat: `printDoc.ts` uses `border-collapse: collapse`, which is exactly the configuration where header repetition is historically flaky — this is a two-line **experiment to run today**, not a proven fix. `@page :left/:right` mirrored margins genuinely are unsupported; that is the only place a polyfill earns its keep.
**Verdict: adopt.** Best ROI on the entire list.

### 2. `docx` 9.7.1 — latent capabilities already sitting in `node_modules` — **ADOPT NOW**
https://github.com/dolanmiu/docx — MIT. **Already installed.**
**Gains (all verified in the installed `index.d.ts`):** `tableHeader?: boolean` (repeat header row in exported .docx), `FootnoteReferenceRun` + `footnotes` on the Document, `CommentRangeStart/End` + `Comments` + `comments`, `InsertedTextRun` / `DeletedTextRun` with `IChangedAttributesProperties` (**native `w:ins`/`w:del` — real track changes on export**), `SimpleMailMergeField` (**native MERGEFIELD**), `bidirectional`, `rightToLeft`, and **`visuallyRightToLeft` on `ITableOptions`** (RTL tables need no XML post-processing; issue #751 is closed).
**Plugs into:** `src/word/docxExport.ts`.
**Effort:** hours per capability. Known defect: with multiple `tableHeader` rows only the first repeats and it bleeds across sections (issue #2425) — workaround is splitting into separate tables.
**Verdict: adopt.** Four wanted features are half-built and nobody noticed.

### 3. `tiptap-text-direction` — **ADOPT NOW**
https://github.com/amirhhashemi/tiptap-text-direction — MIT, v0.5.0, 78★, last commit 2026-06-11.
**Gains:** automatic per-paragraph `dir` detection and persistence — correct for mixed Arabic/English, which is EXELMJ's normal case. Peers `^2.0.0 || ^3.0.0`, **zero runtime deps**.
**Plugs into:** `src/word/direction.ts` — it *collides* with your existing implementation. Pick one owner of the `dir` attribute; the persisted attribute is what `docxExport.ts` needs for `w:bidi`/`w:rtl`.
**Effort:** hours. Does **not** fix bidi in table cells, list markers, or `pdfLayout.ts`.
**Verdict: adopt.** Cleanest win on the list.

### 4. pdf.js `src/core/bidi.js` — port, don't install — **ADOPT NOW**
https://github.com/mozilla/pdf.js — Apache-2.0. `pdfjs-dist` 6.2.108 already pinned.
**Gains:** a UAX#9 subset (W1–W7, N1–N2, I1–I2, L2) with signature `bidi(str, startLevel = -1, vertical = false)` returning `{ str, dir }`. That `dir` is exactly what `direction.ts` and `docxExport.ts` consume.
**Plugs into:** `src/word/pdfLayout.ts` as a `lineDirection(line)` helper; `src/word/pdfToDoc.ts`.
**Effort:** hours. Two real traps: `getTextContent()` already applies bidi per chunk, so reorder at **chunk boundaries only** or Arabic double-reverses; and the subset omits explicit embedding/override/isolate codes, so LRM/RLM-marked PDFs still mis-order.
**Verdict: adopt.** Highest confidence-to-effort ratio after #1.

### 5. `@sereneinserenade/tiptap-comment-extension` — **ADOPT NOW**
https://github.com/sereneinserenade/tiptap-comment-extension — MIT, v0.2.0 (2026-03-29), 512★.
**Gains:** range anchoring for comments — a comment mark carrying a comment id, plus `setComment` / `unsetComment` / `onCommentActivated`. Peers `^2.0.0 || ^3.0.0`, **zero runtime deps**, framework-agnostic core (React/Vue only in the demos). Installs against 3.30.0 unmodified. Tiptap's own `@tiptap/extension-comments` is **404 on public npm** — this is the free path.
**Plugs into:** `src/word/wordApp.ts` (thread state), `src/word/ribbon.ts` (sidebar/gutter), `src/word/docxExport.ts` (ids → `w:commentRangeStart`/`w:comment`).
**Effort:** hours to install, days to build the feature. Threading, resolve state, persistence, sidebar UI and the **RTL gutter flip to the left margin** are all yours.
**Verdict: adopt.**

### 6. `@handlewithcare/prosemirror-suggest-changes` — **ADOPT NOW**
https://github.com/handlewithcarecollective/prosemirror-suggest-changes — MIT, npm 0.1.8 (2025-12-29), repo pushed 2026-08-04, 61★.
**Gains:** real track changes. Four marks (`insertion`, `deletion`, `modification`, `blockBoundarySuggestion`), `withSuggestChanges`, and — note the correct names — `applySuggestion`/`applySuggestions` and `revertSuggestion`/`revertSuggestions` (not accept/reject). Peers are **exactly** `prosemirror-view/model/state/transform ^1.0.0`, all already inside `@tiptap/pm` 3.30: **zero new runtime deps, no React, no Yjs, no server.**
**Plugs into:** `src/word/wordApp.ts` (command wiring) → `docxExport.ts` `InsertedTextRun`/`DeletedTextRun`.
**Effort:** days. No Tiptap wrapper, no UI, no docx bridge — all yours. Repo is 8 months ahead of the last npm publish, so **pin the version**.
**Alternative worth a day of evaluation:** `sungkhum/tiptap-track-changes` (MIT, 16★, peers `^2||^3`, zero deps, vitest suite) — it is a native Tiptap extension and its README *advertises* RTL Arabic/Hebrew testing and 200+ tests. Author-asserted, not independently verified, and bus factor of one. Try it first *because* of the Arabic claim; fall back to suggest-changes if it disappoints.
**Verdict: adopt.**

### 7. `tiptap-footnotes` (buttondown) — **ADOPT NOW**
https://github.com/buttondown/tiptap-footnotes — MIT, npm 3.0.1 (2025-11-28), 79★.
**Gains:** footnote nodes + references in ProseMirror. Peers `@tiptap/core ^3` and `@tiptap/pm ^3`, `dependencies` is literally `{}`.
**Cost the shortlist hid:** it needs `@tiptap/extension-list-item` and `@tiptap/extension-ordered-list` added explicitly (starter-kit 3.x bundles `@tiptap/extension-list` instead), and those pin core **3.30.2** — this is what forces the lockstep bump.
**Plugs into:** `src/word/wordApp.ts` schema, `docxExport.ts` (`FootnoteReferenceRun` + `footnotes`), `printDoc.ts`.
**Effort:** days for the extension; **weeks** for true bottom-of-page placement — out of the box these behave more like endnotes.
**Verdict: adopt** the extension now, defer per-page placement to the paginator work.

### 8. `tafqit` (MohsenAlyafei) — vendor the file — **ADOPT NOW**
https://github.com/MohsenAlyafei/tafqit — MIT (GitHub SPDX confirmed), 78★, repo last pushed 2022-02-28.
**Gains:** Arabic number-to-words (تفقيط) 0 → 10²¹⁺ with masculine/feminine subject agreement and grammatical-case options. Single file, zero dependencies, pure function.
**Plugs into:** new `src/word/tafqit.ts`, consumed by mail-merge fields in Documents mode **and** as a custom function in Univer spreadsheet mode.
**Effort:** hours. **Do not `npm i tafqit`** — npm is stuck at 0.0.1 from 2020; take the file from GitHub, write your own `.d.ts`, own it forever.
**Before shipping:** test the currency arrays against Saudi/Gulf convention (ريال/ريالان/ريالات + هللة), exercise `Legal:'on'` against real contract wording, and check the Arabic-Indic numeral (٠-٩) input path.
**Verdict: adopt.** Pays for itself twice.

### 9. `docXMLater` — vendor, main process only — **ADOPT NOW**
https://github.com/ItMeDiaTech/docXMLater — MIT, npm 12.1.0 (2026-06-29), 14★.
**Gains:** the only library on this list that **emits** RTL OOXML rather than just parsing it — `bidiVisual` on `tblPr` (including inside `tblPrChange`), `w:bidi` on `pPr`/`sectPr`/styles, `w:rtl` on `rPr`, and — the bonus nobody flagged — **`tblHeader` on `TableRow`**, the OOXML repeat-header-row flag. README documents footnotes/endnotes, merge fields, comments with resolve/unresolve, and full tracked-change round-trip. Sole runtime dep is `jszip ^3.10.1`; EXELMJ pins 3.10.1 exactly.
**Plugs into:** `src/word/docxExport.ts` / `docxImport.ts` — **but main process only**: `engines node>=18`, no `browser` field, 222 `Buffer` usages, top-level `import { promises as fs } from 'fs'` in `ZipReader.ts`/`ZipWriter.ts`/`Image.ts`. A renderer bundle will fail to resolve `fs`.
**Effort:** days. Unusually disciplined tooling for 14★ (jest, fast-check, `@xarsh/ooxml-validator`, dependency-cruiser, knip, size-limit). 17.9 MB unpacked is mostly `.map` + shipped `src`; real dist JS ≈ 4.0 MB with `sideEffects:false`.
**Verdict: adopt** — but the README mentions RTL/bidi/Arabic **zero times**, so the RTL code is real yet user-unvalidated. EXELMJ becomes the Arabic test case. **Vendor a pinned copy.**

### 10. The Arabic PDF-output stack: `@pdf-lib/fontkit` (installed) + Amiri + `bidi-js` — **ADOPT NOW**
- `@pdf-lib/fontkit` 1.1.1 (MIT, **already in package.json**) — https://github.com/foliojs/fontkit. `dist/fontkit.es.js` contains `ArabicShaper` and the runtime signature really is `layout(string, features, script, language, direction)`.
  **TypeScript trap:** the bundled `fontkit.d.ts` declares only `layout(string, features?)`. Passing script/language/direction is a compile error though it works at runtime — needs a local declaration merge or a narrow `ts-expect-error`.
- **Amiri** https://github.com/aliftype/amiri — OFL-1.1, 472★, pushed 2026-04-25. Embeddable in a commercial offline app. **Test early:** confirm pdf-lib's fontkit subsetting does not strip GSUB, or Arabic silently renders as disconnected letterforms.
- **`bidi-js`** https://github.com/lojjic/bidi-js — MIT, 1.0.3, zero deps, pure JS. npm frozen at 2023-07-31 but repo commits to 2026-07-01; UAX#9 is a frozen spec so staleness is near-harmless. Battle-tested inside troika-three-text.
**Plugs into:** `src/word/pdfLayout.ts`.
**Effort:** days. Feeding a `GlyphRun` into pdf-lib means writing glyph-level content-stream operators instead of `drawText()`.
**Independent proof this combination works:** `@docx-editor.dev/core@2.5.0` ships `bidi-js 1.0.3` + `harfbuzzjs 1.6.0` as direct runtime deps in a production document editor.
**Verdict: adopt.** Upgrade fontkit → harfbuzzjs later if shaping quality is insufficient.

### 11. `docx-preview` + `@silurus/ooxml` as correctness oracles — **ADOPT NOW (devDependency) / READ**
- `docx-preview` https://github.com/VolodymyrBaydalka/docxjs — Apache-2.0, 0.4.0 (2026-07-07), 2056★, sole dep `jszip` (already present). Renders footnotes/endnotes by default; comments and changes are opt-in and explicitly experimental.
- `@silurus/ooxml` https://github.com/yukiyokotani/office-open-xml-viewer — MIT, v0.80.2, 661★, commits yesterday, **zero runtime deps**, documented UAX#9 bidi + `w:bidi`/`w:rtl` per format.
**Gains:** render your own exported .docx and diff against Word without leaving the machine. Fastest possible feedback loop for `docxImport.ts`/`docxExport.ts`.
**Effort:** hours (devDependency wiring).
**Verdict: adopt `docx-preview` as a dev-only oracle; read `@silurus/ooxml`'s bidi line-breaking.** Never as a pagination source — docx-preview's bidi is a two-branch attribute mapping (`case "bidi"` / `case "rtl"`, verified in the bundle), not a bidi algorithm, and its README states realtime page breaking is not implemented. `@silurus/ooxml` is 14 MB, read-only by design, and its README states the codebase was written by AI agents — correctness is unaudited. Do not ship either.

### 12. Tiptap's ex-Pro extensions now free on public npm — **ADOPT NOW (selectively)**
https://github.com/ueberdosis/tiptap — MIT, all at 3.30.2 published 2026-08-18.
**Free and useful:** `@tiptap/extension-table-of-contents` (adds `uuid ^14`), `-mathematics` (needs KaTeX — **bundle the fonts**), `-unique-id` (adds `uuid`), `-invisible-characters` (Word's ¶ marks), `-details`, `-emoji`, `-file-handler`.
**Still gated (E404 on public npm):** `extension-comments`, `extension-pagination`, `extension-track-changes`, `@tiptap/pages` — i.e. Tiptap sells exactly the four features EXELMJ wants most. That is why items 5, 6, 7 exist.
**New risk:** `@tiptap/extension-drag-handle` declares **hard** peers on `@tiptap/y-tiptap ^3.0.7` and `@tiptap/extension-collaboration` — installing it drags Yjs into an offline single-user app. **adopt-later**, pending a peer-override test.
**Plugs into:** `src/word/wordApp.ts`, `ribbon.ts`.
**Effort:** hours each.

## 2. BY WANTED FEATURE

### Mail merge → **`docx`'s `SimpleMailMergeField` + your own ProseMirror atom node + `exceljs`/Univer as the data source**
Do the merge **in the ProseMirror document, then re-export** — not in the OOXML. Reimplement `talqui-oss/tiptap-extension-variable`'s atom-node design in ~150 lines of TS against `@tiptap/pm` 3.30 (do **not** install it: peers are TipTap 2 only and its picker imports `VueRenderer` from `@tiptap/vue-3` plus tippy.js — both dead in a plain-DOM renderer), and drive the field picker from your existing ribbon UI. New `src/word/mailMerge.ts`: read a sheet via the existing exceljs/Univer side into `Record<string,string>[]`, clone the TipTap JSON per record, replace each `mergeField` node with a text node, and either concatenate with page breaks into one document or emit N files. Export merge-field placeholders as `SimpleMailMergeField` (verified at `index.d.ts` L2802) so a merged-but-unfilled .docx still opens as a real Word merge document. `ONLYOFFICE`'s `Api.LoadMailMergeData`/`Api.MailMerge` is the clearest public description of the intended behaviour — read the docs, never the AGPL code. LibreOffice `sw/source/uibase/dbui/*` and `unomailmerge.cxx` are the second reference; clean-room the **workflow**, never port lines.
**Explicitly rejected alternative: docxtemplater** (see §4).

### Comments → **`@sereneinserenade/tiptap-comment-extension` + `docx` `CommentRangeStart/End`**
Install the mark (zero deps, TipTap 3 native). Store threads in a plain `Map<commentId, {author, ts, text, replies[], resolved}>` owned by `wordApp.ts`, persisted alongside the document JSON. Render the gutter in `ribbon.ts` — and **flip the gutter to the left margin when the paragraph `dir` is rtl**, which is the one detail every Western editor gets wrong for Arabic. On export, emit `CommentRangeStart(id)` / `CommentRangeEnd(id)` around the marked range and a `Comments` part; `docXMLater` is the fallback if `docx`'s comments part proves incomplete on round-trip. Read `wvbe/docxml`'s comment model (point comments, range comments, **replies**) for the threading data shape only — its npm `license` field is the literal string `"none"`, so read, never vendor.

### Track changes → **`@handlewithcare/prosemirror-suggest-changes` (evaluate `sungkhum/tiptap-track-changes` first) + `docx` `InsertedTextRun`/`DeletedTextRun`**
Wrap every editing command in `withSuggestChanges` when suggestion mode is on; the four marks then decorate insertions/deletions/format changes. Build a review pane in `ribbon.ts` that walks the marks and calls `applySuggestion`/`revertSuggestion` per change, plus apply-all/revert-all. Export maps insertion marks → `InsertedTextRun`, deletion marks → `DeletedTextRun`, both carrying `IChangedAttributesProperties` (author + date), which produces **native Word revisions** that a reviewer can accept in Word itself. Do not build this on `prosemirror-changeset` — it gives you spans, not accept/reject semantics, and its GitHub repo is archived (development moved to code.haverbeke.berlin). Known collision to design for up front: **track changes inside footnotes**; Fidus Writer hits exactly this (AGPL — read only, and verify its ModTrack claims in the source before budgeting reading time).

### Footnotes → **`buttondown/tiptap-footnotes` + `docx` `FootnoteReferenceRun`**
Add `@tiptap/extension-list-item` and `@tiptap/extension-ordered-list` explicitly, bump the whole Tiptap set to 3.30.2, then register the extension. Plan a **schema migration** for existing saved documents. Export is trivial: `FootnoteReferenceRun(n)` inline plus `footnotes: { [n]: { children: [...] } }` on the Document. The hard half is **on-screen and printed placement at the bottom of the correct page**, which is a paginator problem, not an extension problem — until the paginator exists these behave as endnotes, which is honest and shippable. `Bindery.js`'s footnote placement pass (MIT, archived 2023) is the best-documented worked example of doing it in a plain browser with no build step.

### Repeating table header rows when printing → **CSS `display: table-header-group` in `printDoc.ts` + `tableHeader`/`tblHeader` on export**
Two independent surfaces, two independent fixes. **Print/PDF:** mark the first row `<thead>` in `buildDocPrintHtml` with `thead { display: table-header-group; break-inside: avoid; }`. Chromium's support here is real but historically fragile under `border-collapse: collapse`, which `printDoc.ts` uses — test against a genuine 3-page Arabic table before believing it, and be ready to switch to `border-collapse: separate; border-spacing: 0`. **Export:** set `tableHeader: true` on the header `TableRow` (`docx`) or emit `tblHeader` (`docXMLater`) so Word repeats it too. Because `tableTools.ts` lets users build tables with no real `thead`, add an explicit "repeat header row" toggle to the table ribbon and let it write the flag — `bookjs-eazy`'s per-cell opt-in model fits EXELMJ better than `<thead>` semantics. WeasyPrint (BSD-3) is the reference implementation for re-emitting header row groups per fragment, and its documented limitation — repeated header/footer groups are incompatible with `border-collapse: collapse` — is the warning that matters most here.

### Arabic spellcheck → **`espells` (MPL-2.0) + AyaSpell dictionary (elect MPL-2.0), fronted by `@farscrl/tiptap-extension-spellchecker`**
The extension is the cheap 20%: MIT, peer `@tiptap/core ^3.0.1`, zero runtime deps, ships no dictionary, and asks you for an object implementing `IProofreaderInterface`. Behind it put `espells` — pure TypeScript, single dep (`iterare`), no WASM, survives a Vite build, runs in a worker. Prefer it over `hunspell-asm`, whose open issues are literally "trouble integrating hunspell-wasm with Vite" and whose embedded Hunspell build is stamped ~Jan 2020. The 80% of the work is the dictionary: `dictionary-ar` is **404 on npm**, so build AyaSpell yourself — clone https://github.com/linuxscout/ayaspell, run its Makefile (the files are `arb_alias.aff` / `arb_alias.dic`, **not** `ar.aff`/`ar.dic`), ship the artefacts **unmodified** with the notice, elect MPL-2.0 in NOTICE, and keep user-added words in a **separate** user dictionary so you never create a derivative of the GPL/LGPL/MPL data. Both engines diverge from real Hunspell precisely on Arabic affix compounding, so budget a tuning pass against a real corpus and default the feature to "suggest, never autocorrect".

### Arabic number-to-words → **`tafqit`, vendored**
See §1 item 8. `TafgeetJS` (MIT, 30★, no push since 2022-12) is the fallback **only** if Gulf currency sub-unit phrasing (هللة/فلس/قرش) reads better — wire tafqit first. **Do not touch `MohsenAlyafei/arqamAR`**: despite being the same author and the richer library (173 currencies), it has **no LICENSE file at all** (GitHub `spdx_id: null`), which means all rights reserved. If you need its depth, open an issue asking for a LICENSE; until then it is off limits.

### Hijri dates → **`Intl.DateTimeFormat` with the `islamic-umalqura` calendar — no library**
Chromium in Electron 43 already exposes this entirely offline: `new Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura', {...})` covers formatting and localisation with zero dependencies and zero installer weight. Wire it as a document field type in `mailMerge.ts`/`templates.ts` alongside the Gregorian date field. Only add `@umalqura/core` (MIT, 19★) if you actually need Hijri-unit **arithmetic** ("due 30 days from today, expressed in Hijri"), which `Intl` cannot do — and if you do, **vendor it**: npm is at **0.0.7 from 2019-07-18** with the repo untouched since 2023-01-07 and 15 open issues. Whatever you pick, surface the Umm al-Qura calculated-vs-sighted one-day discrepancy in the UI for legally sensitive documents.

### Document compare / diff → **`@armantang/html-diff`, vendored, with word-boundary snapping**
MIT, zero runtime deps, 24 kB, 6 files, no open issues — a finished small library rather than an abandoned one, but unpublished since 2024-11-20, so vendor it into `src/word/`. Render `docA`/`docB` to HTML via your existing export path, diff, and display `<ins>`/`<del>`. **The Arabic constraint is a hard design rule, not a caveat:** inserting `<ins>`/`<del>` spans mid-word breaks Arabic cursive joining and visually splits bidi runs, so snap every diff boundary to a word boundary before emitting markup. Table and image handling are undocumented, and nested tables from `tableTools.ts` are exactly where HTML diffs degrade. Durable fallback: `google/diff-match-patch` (Apache-2.0) plus your own HTML tokenizer. For .docx-to-.docx redlining, `JSv4/Docxodus` (MIT, very active, headless core usable without React via the `.` export, `setWasmBasePath()` for offline asset paths) has the richest API — `compareDocuments`, `docxDiffAcceptRevisions`, `getRevisions`, `docxDiffGetConflicts` — but it is a **20.1 MB .NET-in-WASM runtime** with confirmed-absent RTL (one `"rtl"` string in the entire bundle). Adopt-later, and only after you prove Arabic redlines yourself.

### Equations → **`@tiptap/extension-mathematics` (MIT, free) + locally bundled KaTeX fonts**
Now free on public npm at 3.30.2; drops into `wordApp.ts` as a node. Bundle the KaTeX fonts into the asar and verify rendering with the network disabled. `MathLive` (MIT, 2136★, active) is the better *editor* — a plain custom element, so it fits the no-React module — but **do not commit to it until you prove local font loading in a network-disabled build**: the README documents CDN loading, and I could not confirm the `fontsDirectory`/`soundsDirectory` options from any reachable source. The failure mode is equations rendering as empty boxes on the user's offline machine. Either way, RTL support is confirmed **absent** from both: wrap every equation field in `dir="ltr"` isolation inside Arabic paragraphs — mandatory, not optional.

### QR / barcode → **`bwip-js`**
https://github.com/metafloor/bwip-js — MIT (I note GitHub's API reports `NOASSERTION` only because the LICENSE file opens with a custom header; the body is standard MIT — **do not let an automated licence scan reject it**). 2406★, pushed 2026-08-17, pure JS, no runtime deps, renders to canvas **or SVG**. Wrap it in a TipTap node that stores the payload + symbology and renders SVG, so it rides the existing image/SVG path straight into `pdfLayout.ts`. Use per-symbology subpath imports to keep the bundle small. Effort: hours. For Saudi e-invoicing specifically, `@axenda/zatca` (MIT, npm 2021-11-19, repo 2023) computes the Phase-1 TLV entirely locally — **vendor it and write this test first: the TLV length byte must be the UTF-8 *byte* length of the seller name, not the JS string `.length`**, or every Arabic company name silently produces an invalid QR. Phase 2 requires ZATCA CSID over the network and is out of scope.

### Better PDF import → **port pdf.js `bidi.js` now; benchmark `@firecrawl/pdf-inspector-wasm` next; port geometry from PdfPig**
Three layers. **(a) Text order (do this first, hours):** the bidi port from §1 item 4 — this is the single biggest quality jump for Arabic import. **(b) Structure:** `@firecrawl/pdf-inspector-wasm` v1.15.0 is MIT with **zero dependencies**, described as classifying PDFs and extracting structured Markdown from a `Uint8Array` "without uploading data anywhere" — a genuinely offline, no-native-build, renderer-loadable Rust-to-WASM parser, unique on this list. Its README claims RTL support under multi-column layout; that is a claim, so **benchmark it against the user's real Arabic documents before trusting it**, and weigh the WASM installer weight. **(c) Tables:** port algorithms, install nothing. `UglyToad/PdfPig` (Apache-2.0, 2542★, active) is the strongest source — `RecursiveXYCut.cs`, `DocstrumBoundingBoxes.cs`, `UnsupervisedReadingOrderDetector.cs`, `NearestNeighbourWordExtractor.cs` all verified present; RecursiveXYCut is direction-agnostic and RTL-safe, but the reading-order comparator's left-then-top default **must be flipped for RTL pages**. Add `tabula-java`'s split of *detection* (`NurminenDetectionAlgorithm`) from *extraction* (`SpreadsheetExtractionAlgorithm`) — `pdfLayout.ts::tableRun` currently conflates them — and `camelot`'s stream-mode text-edge histogram plus its joints-must-intersect-twice filter (~150 lines into `findBoxes()`). **Universal rule across all of these: take the geometry, never the text ordering.** pdfplumber issue #794 ("Wrong Ordering of RTL Text And Table Extractions", filed 2023-01-20 against an Arabic PDF) is still open and unassigned-to-a-fix; pdf2docx's alignment inference is LTR-centric and will read backwards on Arabic.

## 3. HIDDEN GEMS

- **`SimpleMailMergeField` and `InsertedTextRun`/`DeletedTextRun` in the `docx` you already have.** Two wanted features are partly implemented in a dependency installed months ago. Nothing to install, nothing to licence.
- **`visuallyRightToLeft` on `docx`'s `ITableOptions`.** The widely-repeated "docx cannot do `w:bidiVisual`, see issue #751" is **out of date** — #751 is closed, fixed by PR #795. RTL tables need no XML post-processing and no manual column reversal.
- **`docXMLater`'s `TableRow` emitting `tblHeader`.** A 14★ library nobody has heard of is the only one on this list that writes both `bidiVisual` and the repeat-header flag.
- **`@docx-editor.dev/core@2.5.0`'s dependency list** — `bidi-js 1.0.3` + `harfbuzzjs 1.6.0`. Independent, shipping proof that this exact pairing solves Arabic layout in a document editor. That is worth more than any README.
- **Tiptap Pages' documentation, read as a free bug report.** The proprietary docs state verbatim that non-splittable blocks larger than a page cause an **infinite layout loop** — the layout can only move a whole block forward, a block taller than the page never fits, the editor hangs. *Any* paginator written for `printDoc.ts` must guard this (a full-page image, one tall table row) **before anything else is written.**
- **`tategakibunko/nehan`** (MIT — verified at file level; GitHub's `NOASSERTION` is a false negative). A TypeScript paged-media engine with a genuinely **logical** box model (start/end/before/after) because it was built for Japanese vertical writing. Structurally the right foundation for RTL pagination — though RTL appears nowhere in its docs, so the model *permits* correctness without evidence it *delivers* it. Dormant since 2023-09-07. Read the fragmentation code; never use it as the renderer.
- **`BobLd/DocumentLayoutAnalysis`'s DLA viewer idea.** A debug overlay that draws detected boxes/lines/reading order over the page is the cheapest good idea in this entire inventory for triaging bad `pdfToDoc.ts` imports. **The repo has no licence at all** — copy nothing verbatim; reimplement Docstrum from the 1993 paper (the algorithm is free) and use the repo only to understand threshold values.
- **`Hufe921/canvas-editor`** (MIT, 5117★, very active) — its form **Controls** model for merge-field placeholders, its anchored comment/group-annotation layer, and its cross-page table splitting **with preserved header rows** are three EXELMJ features in one codebase. But I grepped its README *and* CHANGELOG for `rtl`/`bidi`/`arabic`/`عرب` and got **zero hits in each**: every algorithm you port inherits an untested LTR assumption you must fix.
- **`@intevation/tiptap-extension-office-paste`** (MIT, zero deps, peers `^2.10.3 || ^3.0.0`) — pasting from Word into TipTap is a daily-use paper cut nobody budgets for. Frozen since 2025-09-08, so vendor it. Verify against real RTL Word output, and watch its blanket black-colour stripping against your theming.
- **`signature_pad`** (MIT, 5.1.4, 2026-07-31) and **`Cropper.js`** (MIT, 13863★, v2) — hours each, both framework-free, both ride the existing `@tiptap/extension-image` path with no schema change. Cropper v2 is a web-components rewrite, so **every tutorial you find will be v1 API and will not work** — pin deliberately. `signature_pad` is decorative, not cryptographic.
- **`@signpdf/placeholder-pdf-lib@3.3.0`** declares `peerDependencies { "pdf-lib": "^1.17.1" }` — the exact library `pdfLayout.ts` already uses, so PAdES B-B signing drops onto the existing `PDFDocument` with no adapter. Node-only: run it in the main process or a `utilityProcess` and pass bytes over IPC.
- **`@office-kit/docx`** (MIT, 2★, v0.1.1) — sole production dependency `fflate`, ESM, explicitly browser-capable, and its docs cover images, comments, footnotes, headers/footers, bookmarks, hyperlinks and tracked changes. Far too immature to depend on, but the **cleanest short read** of OOXML part-relationship plumbing for exactly EXELMJ's missing feature set.
- **`@umoteam/editor` (Umo Editor)** depends on `@tiptap/core` **3.20.0** — closest to EXELMJ's 3.30.0 of anything on this list, which makes its ProseMirror-level pagination code the most transferable. (Correcting a common claim: current npm is **v11.1.1**, not a "v4.6 line", and there is **no pagination-deprecation notice** anywhere in the README.) The barrier is structural, not licensing: Vue 3 UI, Chinese docs, no RTL mention anywhere.

**Rejected on technical grounds (licence is fine):**

- **`docxtemplater`** (dual MIT/GPLv3 core) — **rejected for mail merge.** The free core does text substitution, loops and conditions only. Its own README confirms the paid catalogue includes exactly what a real merge needs first: Image, HTML, XLSX, Chart, Word-Run, QrCode, Table, Styling, **Footnotes** and Paragraph Placeholder modules. Same paid-tier trap as Tiptap and EigenPal. And architecturally it merges into a stored `.docx` template, not the live editor document. If you ever want a template engine anyway, **`easy-template-x`** is fully MIT (v7.2.6, 530★, deps `@xmldom/xmldom` + `json5` + `jszip 3.10.1` **exactly matching your pin** + `lodash.get`) — but verified by clean extraction: its shipped bundle has **0 hits** for `bidi`, `rtl`, `bidiVisual` and `MERGEFIELD`, so no Arabic handling and no Word-native merge fields, only its own `{tag}` syntax.
- **`docx-templates`** — clean MIT, and it adds only `sax` on top of your existing jszip. **But the common mitigation advice is wrong:** there is no safe mode. The official docs state Node's `vm` module "is explicitly not meant to be used as a security mechanism" and warn of code-injection risk. Templates are executable code. The only defensible rule in an Electron app: never open a `.docx` template the app did not generate itself.
- **`@eigenpal/docx-editor` / `@docx-editor.dev/core`** — the project is **alive** (208★, 2.5.0 published 2026-08-18, live demo, hosted docs) and the core is genuinely framework-agnostic Apache-2.0 with pure ProseMirror peers, contradicting the usual "dead, React-only" framing. **But the split licence is the trap:** the README states verbatim that every package is Apache-2.0 **except** `editor-api` and `pro`, which carry the "EigenPal Pro Evaluation License 1.0" — free to evaluate, production use requires a commercial agreement — and the README lists **tracked changes, comments and custom nodes as PRO features**. The two things EXELMJ wants most are behind the paywall. It also pulls its own `prosemirror-model/state/view`, duplicating `@tiptap/pm` 3.30 unless deduped. **Read it for the `bidi-js` + `harfbuzzjs` proof; do not design around it.**
- **`docx4js`** — MIT but pinned to `jszip ^2.6.0` against your 3.10.1 (incompatible APIs, two zip stacks), plus `cheerio 0.22` and `htmlparser2 3.x`, decade-old lines with unpatched-advisory exposure. Dormant. `@silurus/ooxml` teaches the same traversal lesson and is current.
- **`wax-prosemirror`** — MIT, but it **exact-pins** `prosemirror-model 1.19.0`, `prosemirror-view 1.30.2`, `prosemirror-state 1.4.3`, `prosemirror-transform 1.7.1`. Installing it beside TipTap 3.30 gives you two ProseMirror instances and breaks plugin/schema identity at runtime. Add React 19 + styled-components + i18next + inversify + moment peers and it is structurally impossible here. Port the threaded-comment anchoring by hand.
- **`tiptap-extension-pagination` (hugs7)** — peers are `@tiptap/core ^2.11.5` — **TipTap 2 only**, no v3 path. (Also: MIT in the repo, ISC on npm.) `@adalat-ai/page-extension` is likewise TipTap-2-only **and** React-mandatory. `tiptap-pagination-breaks` declares `@tiptap/core` as a real dependency rather than a peer — duplicate ProseMirror risk. **`tiptap-pagination-plus`** is the only pagination package whose peers (`^2||^3`) actually allow 3.30, but it has **zero tests** (`scripts.test` is `echo "Error: no test specified" && exit 1`), **no LICENSE file** despite declaring MIT, and repo/npm drift (repo says 3.0.6, npm ships 3.1.0) — so the code you install is not the code you can read. Get a LICENSE committed before considering it.
- **`regionize`** (MIT) and **`Bindery.js`** (MIT) — both **archived read-only 2023-04-04**; Bindery's last npm publish was 2021-01-10. regionize explicitly "makes no attempt to handle the styling of elements that break across regions" and I found **no** table/`thead` handling at all. Vendorable, but budget them as adopting an orphan.
- **`paged.js`** — MIT and the obvious candidate, but **confidence downgraded**: I read the docs index and margin-boxes page and found **no mention of footnotes** and **no mention of repeating table headers** — the two features that would justify adopting it. Also drags in lodash, `css-tree 1.0.0-alpha.29`, and the **deprecated `@babel/polyfill`**, npm frozen at 0.4.3 (2023-07-06), no RTL mention. Verify both features against the live library before writing any integration; if you do use it, run it on a detached print clone, never the live editor.
- **`@ansonlai/docx-redline-js`** — MIT and real, but the value proposition collapses: it exists to save you hand-writing `w:ins`/`w:del`/`w:rPrChange`, which **`docx` 9.7.1 already emits natively**. What remains is `diff-match-patch`, callable directly in four lines. 13★, 0.2.x, and its npm description advertises "zero-dependency" while declaring a dependency.
- **`@turbodocx/html-to-docx`** — MIT and active, but its dependency tail includes **`axios`** (to fetch remote images) and I could not confirm it is unreachable at runtime: **never ship it**. Decisive functional flaw: `direction: 'rtl'` is a single **document-level** switch, not per-paragraph `w:bidi`, so it cannot model mixed Arabic/English — EXELMJ's normal case. Fine as a devDependency second opinion; read it for how it threads header/footer HTML.
- **`pdfexcavator`** — depends on **`pdfjs-dist ^4.7.76`**, two majors behind your pinned 6.2.108 (duplicate pdf.js or a patch), optional deps include **`canvas` (a native build)** and tesseract.js, and it needs `fs`/`path`. 9★, 16 commits, RTL absent. Read `src/`, port the column-profile splitter and the confidence-scored table candidate beside `groupLines()`; never `npm install` it.
- **`mammoth.js`** — BSD-2, 6284★, genuinely healthy, and it declares a real `browser` field so it is renderer-safe with no bundler surgery. Rejected as the primary importer only because **by design it discards colours, fonts, sizes and direct formatting** — which is most of what Documents mode cares about. Keep it as a fallback importer; its style-map DSL is genuinely valuable for Arabic institutional templates.
- **`tesseract.js`** — Apache-2.0, 38k★, and it *does* work offline **but not by default**: `langPath` and core WASM are fetched from jsDelivr unless you set `workerPath`, `corePath` **and** `langPath` to local paths. That is the difference between working and silently failing on the user's disconnected machine. Adopt-later, only if scanned-PDF import becomes a real requirement.
- **`libtashkeel`** — MIT, 52★, but **Rust** (not C++), with **no npm package, no prebuilt WASM, no documented browser build**, and an undocumented ONNX model size. Do not plan around it until someone produces a working `.wasm` and measures the model. If it ever ships: diacritisation is ambiguous, so present it as accept/reject suggestions, never a silent transform.
- **`Ar-PHP`** — dual LGPL-3.0 **or** Waqf PL v2.0 (confirmed verbatim in the README), so you may simply elect LGPL and ignore the religious-purpose licence. PHP, so nothing installs; you port algorithms and public Unicode tables by hand — its `Glyphs` (joining/ligature selection) and `Numbers` (tafqit) modules are the two worth it. **Unverified:** the claimed v7.0.0 Arabic spell checker — the README's release badge points at v6.3.1. Confirm before planning around it.
- **`camelot`, `pdfplumber`, `nlm-ingestor`, `PDFact`, `tabula-java`, `LibreOffice core`, `Fidus Writer`, `nassij`, `pdf-text-extraction`, `docx-to-prosemirror`** — all read-only by construction (Python/Java/C++/PHP, or server-dependent). Notes: **PDFact is abandoned** (no push since 2022-01-04) and tuned for two-column scientific LaTeX. **`nassij`** is a 1★ solo repo depending on EasyOCR + PaddleOCR (model downloads, unusable offline) — read only the tashkeel-recombination pass, ignore the marketing. **`docx-to-prosemirror`** has **four commits total**; treat it as a checklist of docx constructs, never an authority. **`pdf-text-extraction`** has no WASM/npm bindings anywhere — its value is purely the sequencing insight (group into lines geometrically **first**, then bidi the assembled line) plus its ICU integration point.

## 5. WHAT I WOULD DO FIRST

Chosen for an Arabic office user producing letters, quotations, minutes, memos and bank statements.

**1. Unlock what is already installed + fix print fragmentation — ~1 day**
`docx`'s `visuallyRightToLeft` on every exported table, `tableHeader: true` on header rows, `bidirectional`/`rightToLeft` wired to the paragraph `dir`; plus the `thead { display: table-header-group }` experiment in `printDoc.ts` and `displayHeaderFooter` + `pageNumber`/`totalPages` templates in the `printToPDF` call. **Zero new dependencies.** This alone fixes RTL tables in exported Word files and gives multi-page bank statements a repeating header and "صفحة X من Y". Files: `docxExport.ts`, `printDoc.ts`, `pageSetup.ts`.

**2. Text direction + PDF-import bidi — ~2 days**
Install `tiptap-text-direction` and resolve ownership of the `dir` attribute against `direction.ts`; port pdf.js `bidi.js` into a `lineDirection()` helper for `pdfLayout.ts`, reordering at chunk boundaries only. Fixes the single most visible daily defect: mixed Arabic/English paragraphs and imported PDFs reading backwards. Files: `direction.ts`, `pdfLayout.ts`, `pdfToDoc.ts`.

**3. Mail merge — ~1 week**
A `mergeField` atom node (~150 lines, reimplemented, not installed), a field picker in `ribbon.ts` fed by the existing exceljs/Univer sheet, a per-record document cloner in a new `mailMerge.ts`, and `SimpleMailMergeField` on export. Ship **tafqit** (vendored) in the same week as a field type — an amount that writes itself in correct Arabic words is the difference between a quotation template and a toy. Add the `Intl` Hijri date field here too: it costs an hour and no dependency. **This is the highest-value *new* feature for quotations and letters.** Files: new `mailMerge.ts`, new `tafqit.ts`, `templates.ts`, `ribbon.ts`, `docxExport.ts`.

**4. Comments — ~1 week**
Install `@sereneinserenade/tiptap-comment-extension`, build the thread store in `wordApp.ts`, the gutter in `ribbon.ts` (**left margin when `dir=rtl`**), and `CommentRangeStart/End` + the comments part on export. Minutes and memos circulate for review; this is what turns EXELMJ from a document producer into a document *workflow*. Files: `wordApp.ts`, `ribbon.ts`, `docxExport.ts`.

**5. Track changes — ~1.5 weeks**
One day evaluating `sungkhum/tiptap-track-changes` against real Arabic text (its advertised RTL testing is the reason to try it first), then commit to it or to `@handlewithcare/prosemirror-suggest-changes`. Build the review pane, wire `applySuggestion`/`revertSuggestion`, and map the marks to `InsertedTextRun`/`DeletedTextRun` so the result opens as native revisions in Word. **Do the Tiptap 3.30.0 → 3.30.2 bump before this step**, since footnotes come next and need it. Files: `wordApp.ts`, `ribbon.ts`, `docxExport.ts`.

*Deliberately after these five:* footnotes (needs the version bump and is endnote-shaped until a paginator exists), Arabic spellcheck (the dictionary build and false-positive tuning are a multi-week project on their own), equations, and any pagination rewrite — the last of which must start by guarding the infinite-loop case Tiptap documented before a single line of layout code is written.
